## 问题

### Critical

#### C1. `close_session` / `abort` 不会终止子进程；emitter 任务永久泄漏，子进程退出后成为僵尸
- **位置**：
  - `crates/omp-tauri/src/commands.rs:198-211`（emitter 任务 `let _session = session; while let Ok(ev) = rx.recv().await {...}`）
  - `crates/omp-tauri/src/commands.rs:250-263`（`close_session` 只从 map 删除 `Arc<SessionHandle>`）、`:265-273`（`abort` = `close_session`）
  - `crates/omp-host/src/session.rs:43-58`（`SessionGuard` 注释声称“drop 即杀”，实际是空 marker）、`:116-122`（`SessionHandle` 自己持有 `events: broadcast::Sender`）、`:60-63`（`Child` 在 `Session` 里）、`:104`（`kill_on_drop(true)`）
- **问题**：真正的 `tokio::process::Child` 由 `Session` 持有，而 `Session` 被移进 emitter 任务（commands.rs:202）。`close_session` 只是把 map 里的句柄删掉；由于 `Session` 内的 `SessionHandle` 自己持有 broadcast **Sender**，而 stdout/stderr pump 也各持 clone，`rx.recv()` 永远不会得到 `Closed`，任务永久停在 `recv().await`。`kill_on_drop` 只有在 `Child` 被 drop 时才生效，而该 drop 不可达。`SessionGuard` 是空结构体，`close_session` 删掉最后一个 `Arc` 什么也不会发生。
- **影响**（核心流程 broken + 资源泄漏）：
  - 前端 Stop（`useComposer.ts:146`）→ `abort` → 界面显示已停，但 `omp` 子进程继续跑完整个 turn（继续调工具/改文件/产生费用）；用户无法中止。
  - 关闭会话后进程继续存在；即使 `omp` 自然退出，`Child` 也永远不被 `wait`/drop → **僵尸进程**（tokio 的 orphan reaper 也依赖 drop），长跑 GUI 会积累。
  - `AppState.sessions` 条目永不清理，`Session`/pump 任务/pipe fd 泄漏。
- **修复建议**：让 `SessionHandle` 持有可控的终止原语（`Arc<AtomicBool>` + `tokio::sync::Notify`，或 `Arc<Mutex<Option<Child>>>`），由 `close_session` 显式 `kill().await` + `wait().await`；emitter 任务改为 `tokio::select! { ev = rx.recv() => ..., _ = handle.closed() => break }`；任务退出前 `drop(session)` 前先 `kill+wait`；`SessionGuard` 要么实现真正的 `Drop`（`start_kill`）要么删除，文档不要声称与实现相反的行为。

#### C2. IPC 参数契约整体不匹配：所有“带状态”的命令都要求 `args` 包装且字段为 snake_case，前端全部发扁平对象
- **位置**：
  - Rust：`commands.rs:23-69`（`SpawnSessionArgs/SendPromptArgs/SendUiResponseArgs/CloseSessionArgs/WorktreeArgs/CreateWorktreeArgs/RemoveWorktreeArgs` 无 `rename_all`，内部键为 `session_id/request_id/repo_path/base_branch` 等）；命令形参名为 `args`：`:185, :225, :239, :253, :268, :282, :296, :306, :320`；`pty.rs:90-94`（`args: PtySpawnArgs`）
  - 前端：`useComposer.ts:64`（`{session_id, prompt}`）、`useTranscript.ts:366`、`useApproval.ts:32-36`（`{session_id, request_id, response}`）、`useWorktree.ts:89/109/132/154`（`{repoPath, path, branch, baseBranch, force}`）、`useTerminal.ts:41-45`（`pty_spawn {shell, cols, rows}`）
- **问题**：Tauri 2 命令参数默认按 camelCase 解析（`tauri-macros-2.7.4/src/command/wrapper.rs:51`）。Rust 命令只有一个形参 `args: XxxArgs`，因此 JS 必须发 `{ args: {...} }`；`XxxArgs` 内部又走 serde 默认命名（snake_case），所以还必须发 `session_id`/`repo_path`/`base_branch`。前端实际发的是扁平对象，且 worktree 系列字段为 camelCase（`repoPath`）。结果：`send_prompt`/`send_ui_response`/`close_session`/`abort`/worktree 全部/`pty_spawn` 都会在 IPC 层被拒（`missing required key args` / 字段反序列化失败），**到不了 handler**。
- **影响**：M2 的会话、审批回传、worktree、Terminal 打开全部不可用；这是“看起来写完了但一条命令都调不通”的契约级 break。叠加 C3（crate 无法编译）与“`spawn_session` 无前端调用者”（grep 全仓确认 + `Sidebar.tsx:46-49` 用 `MOCK_SESSIONS` 的 `"1"/"2"/"3"` 冒充 session id），真实会话链路从 spawn 起就是断的。
- **修复建议**：二选一并固定为契约：(a) 把命令改成扁平形参（`session_id: String, prompt: String`，JS 侧用 camelCase key 如 `sessionId`）；或 (b) 保留 `args` 包装，前端统一发 `{args:{session_id,...}}`。无论哪种，给 `*Args` 加 `#[serde(rename_all = "camelCase")]` 后在前端用 camelCase（推荐，符合 TS 习惯），并加一个“Rust 命令签名 ↔ 前端 invoke 参数”的契约测试/生成物。另需补 `spawn_session` 的真实调用方（新建会话按钮）。顺带：`pty_write/pty_resize/pty_kill`（`pty.rs:173-206`）与 `diff_compute`（`commands.rs:329-335`）的扁平签名当前是对的，改动时别破坏。

### Important

#### I1. `diff_compute` 在两侧行数不等时会越界 panic；输出也不是合法/可用的 unified diff
- **位置**：`crates/omp-tauri/src/commands.rs:340-390`（越界切片 `:371-372`；`best` 搜索用严格 `<` 于 `:354-367`，回退 `(1,1)` 于 `:368`）
- **问题**：当 old 行先耗尽（`oi == old_lines.len()`）而 new 还有行，或反之，`while` 条件仍成立；`best` 的搜索条件 `oi+skip_o < old_lines.len()` 永假 → `best=None` → `(skip_o, skip_n)=(1,1)` → `old_lines[oi..oi+1]` 在 `oi==len()` 时越界 panic。`node` 复刻验证：old `a\nb\nc` → new `a\nb\nc\nd` 必触发。任何“追加/删除尾部行”的 diff 都是这种形状。另外该算法只输出变更行、不输出上下文，hunk header 的 count 只统计变更行（不是标准 unified diff 的 old/new 区间行数），`diff2html`/标准工具会解析错误；`best` 的 `<` 还永远匹配不到文件最后一行。
- **影响**：一旦 `diff_compute` 可达（前端 `useDiff.ts:94-99` 的 `'__TAURI__' in window` 判据修好后即会调用），追加内容的最常见 diff 会让命令 panic。异步命令在 Tauri 中经 `respond_async_serialized`（`tauri-2.12.5/src/ipc/mod.rs:329/375`）spawn，panic 被 tokio 捕获后 **invoke 永不 resolve**，Diff tab 永久 loading（是否整体 abort 需运行时确认）。即使不 panic，输出质量也不足以支撑 M5 的 diff 高亮。
- **修复建议**：直接使用成熟 crate（`similar` 或 `imara_diff`）生成标准 unified diff，并限制输入大小（如 >10MB 拒绝或截断）；至少先修越界：两侧任一耗尽时只输出单侧行。补测试：尾部追加、尾部删除、old/new 完全不等、空文件、最后一行变更。

#### I2. broadcast `Lagged` 被当成“通道关闭”，会静默杀掉正在流式的会话
- **位置**：`crates/omp-tauri/src/commands.rs:204-210`（`while let Ok(ev) = rx.recv().await { ... }`）、`crates/omp-host/src/session.rs:30`（`EVENT_CAPACITY = 256`）
- **问题**：`tokio::sync::broadcast::Receiver::recv()` 在消费者落后时返回 `Err(RecvError::Lagged(n))`；`while let Ok(..)` 把它当成结束条件，循环退出 → emitter 任务结束 → `Session` 被 drop → `kill_on_drop` 杀掉子进程。容量 256 对 5000 消息 fixture 回放/高频 delta（每个 `message_update` 还带完整 `partial`，约 1-2KB）并不宽裕；只要 emitter 一时落后就整会话死亡。
- **影响**：流式输出高峰或 webview 卡顿（大 transcript 渲染）时，会话被无故终止且前端收不到任何错误事件（见 I7），用户只看到停在半截的 turn。
- **修复建议**：`match rx.recv().await { Ok(ev) => ..., Err(Lagged(n)) => { warn!(); 可选 emit Error/继续 }, Err(Closed) => break }`；同时把“事件丢失”可见化（计入 UI 调试日志）。

#### I3. 首帧 `maxFrameBytes` 升级时丢弃已缓冲的半帧，真实协议下会吃掉 `available_commands_update`（18.8KB）
- **位置**：`crates/omp-host/src/session.rs:147`（初始 `LineSplitter::new(1024)`）、`:153-178`（同一 chunk 内先处理所有行，再 `splitter = LineSplitter::new(m)` 整体替换）
- **问题**：`LineSplitter::push(chunk)` 会把未以 `\n` 结尾的残帧留在 `self.buf`；一旦在**同一个 8KB read chunk** 里解析到 `ready` 的 `maxFrameBytes`，代码直接 `splitter = LineSplitter::new(m)`，`buf`（可能包含后续大帧的前半段）和 `discarding` 状态一起被丢弃。真实抓包 `fixtures/clean_round.jsonl` 第 4 行 `available_commands_update` 长 18800 字节（node 实测），而 read buffer 是 8192（`session.rs:148`）；若 `ready` 与下一行前半段被一次 read 取回，后者的前半段丢失，后半段会被当作从 JSON 中间开始的 `Noise`。此外同一 chunk 里在升级前解析到的大行仍按旧上限 1024 判 `Oversized`。
- **影响**：slash 补全的数据源（`available_commands` 事件）可能丢失或错位，前端 Slash 菜单为空；也会污染 `Noise` 通道。是否触发取决于管道分块（需运行时确认），但“替换 splitter 丢缓冲”是确定的缺陷。
- **修复建议**：给 `LineSplitter` 加 `set_max_frame_bytes(&mut self, n)` 保留 `buf`/`discarding`；或先扫描 `maxFrameBytes` 再解析本 chunk；初始上限用协议默认值（如 1MiB）而不是 1024。

#### I4. PTY `write` 每次调用都 `take_writer()`，从第二次按键起必然失败
- **位置**：`crates/omp-tauri/src/pty.rs:36-48`（`:41-43` 每次 `master.take_writer()`）
- **问题**：`portable-pty-0.9.0/src/unix.rs:357-364` 的 `UnixMasterPty::take_writer()` 用 `took_writer: RefCell<bool>` 保证只可成功一次，第二次返回 `"cannot take writer more than once"`；Windows conpty 同理（`src/win/conpty.rs:99-108`）。
- **影响**：Terminal 只能成功写入第一个字符/第一次输入，之后所有 `pty_write` 报错；交互式 shell 实际不可用（叠加 I5 后是完全不可用）。
- **修复建议**：在 `PtyEntry` 构造时 `take_writer()` 一次，存入 `Mutex<Box<dyn Write + Send>>` 长期复用；`pty_write` 只做加锁写入（可考虑异步 writer task + channel，避免在 async 上下文里同步写阻塞）。

#### I5. PTY 输出通道契约完全对不上：后端不推送 `pty://<pid>/data|exit`，前端也不轮询 `pty_read`
- **位置**：`crates/omp-tauri/src/pty.rs:131-166`（只发一个 `FrontendEvent::Noise` "pty N exited" 到 `omp://event`）、`:208-219`（`pty_read` 轮询接口）；前端 `src/hooks/useTerminal.ts:48-62`（监听 `pty://${pid}/data` / `pty://${pid}/exit`，从不调用 `pty_read`）
- **问题**：后端注释（`pty.rs:131-132`）声称“前端轮询 `pty_read`”，但前端实现是事件订阅；Rust 侧 grep 无任何 `pty://` 发送。于是输出永远不会到 xterm，退出也不会通知 UI。另有：

  - `pty_read` 用 `String::from_utf8_lossy(&guard)` 切分（`:216`），多字节 UTF-8 跨轮询被截断会产生替换字符（中文输出乱码）；
  - 缓冲超过 1MiB 时 `guard.clear()`（`:143-145`）静默丢光已有数据（应保最新）；
  - `exited` 标志（`:32,128,153`）无人读取；
  - 进程退出后 registry 条目不清（`:196-206` 只有 `pty_kill` 删除），fd/内存泄漏。
- **影响**：Task 6 验收“Terminal 连本地 shell”失败；即便补上事件，UTF-8/溢出处理也会带来乱码与丢输出。
- **修复建议**：明确一种通道（推荐 spec §4 的“event 推 output、command 收 input”）：reader 任务按块 `emit` 到 `pty://<pid>/data`，退出时 `emit` `pty://<pid>/exit` 并从 registry 移除；UTF-8 用增量解码（保留未完成尾部字节）；溢出策略保留最新 N 字节并通知一次；`pty_spawn` 增加 `cwd`（前端目前没传，见偏差）与 `TERM` 环境变量。

#### I6. PTY reader 在 async 任务里做阻塞 `std::io::Read`
- **位置**：`crates/omp-tauri/src/pty.rs:133-155`（`tauri::async_runtime::spawn(async move { ... reader.read(&mut buf) ... })`）
- **问题**：`portable_pty::MasterPty::try_clone_reader()` 返回阻塞 reader；在 tokio worker 上阻塞 `read` 会占住一个 worker 线程直到 shell 退出。每个 Terminal tab 一个 PTY，多 tab 会逐步吃掉 runtime 线程。
- **影响**：Terminal 打开几个 tab 后整个 Tauri 异步执行器吞吐下降（命令、会话事件 pump 都可能被饿到）；与 I2 叠加会放大 Lagged。
- **修复建议**：reader 循环放进 `spawn_blocking`，经 `tokio::sync::mpsc`/直接 `emit` 把数据送回 async 侧；或者使用 `tokio::io::unix::AsyncFd` 包装 master fd。

- **位置**：`git ls-tree HEAD crates/omp-tauri` 只有 6 个文件；工作区中 `build.rs`、`capabilities/default.json`、`permissions/autogenerated/*`、`gen/**`、`src/pty.rs` 及 Task 4–7 的全部改动均未提交；`.gitignore:1` 仅 `/target`

#### I15. Tauri 全局对象与 store 插件契约不匹配（配置侧）：`withGlobalTauri` 缺失导致前端 Tauri 分支永不执行；`plugin:store|*` 缺 `rid`
- **位置**：`tauri.conf.json:11-31`（无 `withGlobalTauri`；`tauri-utils-2.10.2/src/config.rs:5039` 默认 false）；前端 `useTerminal.ts:31,39`、`useDiff.ts:94`、`useWorktree.ts:72`、`usePreview.ts:16` 用 `'__TAURI__' in window` 判定；`useStore.ts:8-14,26-33`、`useTheme.ts:26,44-47`、`i18n/index.ts:31-32` 直接 `invoke('plugin:store|get/set/save')`；`tauri-plugin-store-2.5.0/src/lib.rs:147-165,238-240` 要求 `rid`，`get` 返回 `(Option<JsonValue>, bool)`
- **问题**：真实应用里 `window.__TAURI__` 不存在（除非 Tauri CLI 注入 `withGlobalTauri`），所以 Terminal/Diff/Worktree/Preview 的 `isTauri` 分支永远不会走，全部落到浏览器/Node fallback（在 Tauri webview 里 Node fallback 也不可用，`runGitCommand` 依赖 `child_process`）。同时原生 Tauri 命令调用（store）缺少 `rid`，`invoke` 会报错并被 catch 成默认值 → 布局/主题/语言持久化静默失效；`plugins.store.autoSave`（tauri.conf.json:43-47）在 store 2.5.0 中也没有对应 config 结构，形同虚设。
- **影响**：M2 声称的 store 持久化、Terminal、Diff、Worktree 在真实应用里都不会进入后端路径；即使 C2 修好参数，前端仍可能因判据问题不走 Tauri。
- **修复建议**：二选一并统一：设置 `app.withGlobalTauri: true`（简单，但与前端 `@tauri-apps/api` 动态 import 重复），或把所有 `'__TAURI__' in window` 判据换成 `isTauri()`（`@tauri-apps/api/core` 的 `isTauri`）/**完全去掉 fallback**（桌面应用不需要浏览器 mocks）。store 侧用 `Store.load("layout.json")`（`@tauri-apps/plugin-store`）拿到实例再 `get/set/save`，或传递 `rid`；删除无效的 `plugins.store` 配置。

#### I16. 会话 ID 生成可能碰撞，map 覆盖导致旧会话不可寻址
- **位置**：`crates/omp-host/src/session.rs:292-301`（`subsec_nanos ^ (pid << 32)`）、`commands.rs:213-217`（`insert` 直接覆盖同 id）
- **问题**：`subsec_nanos()` 只取当前秒内纳秒（<1e9），跨秒完全可能重复（例如每秒整点附近 spawn，两次会得到相同尾数）；同一进程内两次并发 `spawn_session` 在时钟粒度粗时也可能相同。`HashMap::insert` 会覆盖旧句柄，旧会话变成“不可寻址但仍在运行”的孤儿（且因 C1 无法停止）。
- **影响**：session_id 路由错乱（`send_prompt` 发到新会话）、旧会话泄漏；在 M4 多会话/自动化批量 spawn 下风险更高。
- **修复建议**：用进程内 `AtomicU64` 自增 + 随机后缀（或 `uuid`/`getrandom`），并检查 `HashMap` 是否已存在（存在则重试）。

## 结论

**FAIL。**

阻断理由（任何一条都足以让 M2 后端不可交付）：

1. **生命周期核心缺陷（C1）**：`close_session`/`abort` 不杀子进程，emitter 任务与 `Child` 永久泄漏、退出后僵尸；Stop 功能形同虚设。
2. **IPC 契约全断（C2）**：所有有状态命令因 `args` 包装/字段命名不匹配而调不通；`spawn_session` 无前端调用者，真实会话链路从起点断开。
3. **crate 无法编译（C3）**：`frontendDist` 路径不存在 + `icons/` 缺失导致 `generate_context!` 编译期 panic，`cargo check -p omp-tauri`（Task 1 验收）不可能通过，Task 4–7 的 Rust 代码从未编译过；叠加 `devUrl` 缺失与 Vite `outDir` 错位。
4. **终端/工具/审批等横切契约（I4/I5/I7/I12）**：PTY 只能写一次、输出通道双向对不上、tool 事件降级为 Noise、worktree 前后端数据结构不一致。

**复测前的最小修复集**（按顺序，全部完成后再审）：
1. C3：修正 `devUrl`/`frontendDist`/`outDir`，`cargo tauri icon` 生成并提交 icons；跑通 `cargo check -p omp-tauri`。
2. C2：统一 IPC 参数形态（建议 `rename_all = "camelCase"` + 扁平参数），补 `spawn_session` 调用方；加 Rust↔前端参数契约测试。
3. C1/I8/I10：显式 kill+wait 的会话收尾、`SessionClosed` 事件、应用退出清理；`Lagged` 不杀会话（I2）。
4. I4/I5/I6：PTY writer 复用、事件化输出、阻塞读移出 async 线程、UTF-8 增量解码。
5. I7/I12：补 tool 事件桥；worktree 用 `-b` + 结构化返回 + 路径校验。
6. I13：换真实 fixture 的集成测试（含 close 后进程退出断言），去掉静默 skip；补 omp-tauri 命令测试。

维修完后建议先跑：`cargo check -p omp-tauri`、`cargo test --workspace`（含 shim）、`npm run tauri build --no-bundle`（验证前端资源嵌入）、`npm run e2e`，再做 M2 验收。

> 审查立场说明：以上结论均基于对磁盘代码与锁定依赖源码的静态核对；少数“需运行时确认”的点（Tauri 异步命令 panic 的最终表现、真实 omp 首包分帧时序、GUI 退出后子进程是否自行退出）已随条目注明，未作为 Critical 依据。
